# sandbox-executor

*[Read in English](./README.md)*

Запускает shell-команду в изолированном контейнере Docker с ограничением ресурсов
и возвращает результат. Это вся его работа — пакет ничего не знает про «проект»,
«сборку», «деплой», «задачу» или любую другую сущность вызывающей стороны.
Вызывающий передаёт образ, команду, лимиты и (опционально) stdin; в ответ
получает stdout, stderr, код завершения и длительность.

Это самостоятельный пакет без зависимости на кодовую базу какого-либо конкретного
потребителя — рассчитан на то, чтобы им пользовались сразу несколько проектов,
которым нужно запускать недоверенные или частично доверенные команды в изоляции,
вместо того чтобы каждый проект встраивал свою копию этой логики.

## Зачем это нужно

Разным вызывающим сторонам нужна одна и та же операция — выполнить команду в
изолированном контейнере с лимитами и получить результат — но с совершенно разным
содержимым на входе: один может использовать её для шагов `install`/`test`/`build`
CI-сборки, другой — чтобы прогнать решение против скрытых тестов. Механизм
один и тот же, содержимое разное, поэтому это отдельный небольшой пакет, а не код,
задублированный или перемешанный с доменной логикой каждого потребителя.

## Установка

Через [bun](https://bun.sh):

```bash
bun add github:<you>/sandbox-executor#v0.1.0
```

Либо добавить вручную в `package.json` и выполнить `bun install`:

```jsonc
// package.json потребителя
{
  "dependencies": {
    "sandbox-executor": "github:<you>/sandbox-executor#v0.1.0"
  }
}
```

Работает так же с обычной git-ссылкой вместо `github:owner/repo`
(`bun add git+ssh://git@example.com/sandbox-executor.git#v0.1.0`) — это нужно для
приватного репозитория без GitHub-специфичного сокращения.

У git-зависимости нет шага publish на npm-реестре, а значит никто не соберёт её
за потребителя — поэтому `dist/` коммитится в репозиторий, а не игнорируется:
после `bun add` сразу оказывается рабочий собранный JS, без отдельного шага
сборки. Если меняете `src/` — прогоните `bun run build` и закоммитьте обновлённый
`dist/` перед тем, как ставить новый тег версии.

## Использование

```ts
import { execute } from 'sandbox-executor';

const result = await execute({
  image: 'node:20-bookworm-slim',
  command: 'npm test',
  workdir: '/absolute/host/path/to/checkout', // монтируется в контейнер как /workspace
  timeoutMs: 5 * 60 * 1000,
  memoryLimitMb: 512,
  cpuLimit: 1,
  network: true, // установщикам/тест-раннерам обычно нужен доступ к реестру
  onOutput: (chunk) => process.stdout.write(chunk.text),
});

console.log(result.exitCode, result.durationMs, result.timedOut);
```

## API

```ts
interface ExecuteOptions {
  image: string;
  command: string;
  stdin?: string;
  timeoutMs: number;
  memoryLimitMb: number;
  cpuLimit: number;
  workdir?: string;   // путь на хосте, монтируется в контейнер как /workspace
  network?: boolean;  // по умолчанию false — сеть наружу выключена
  onOutput?: (chunk: { stream: 'stdout' | 'stderr'; text: string }) => void;
}

interface ExecuteResult {
  stdout: string;
  stderr: string;
  exitCode: number | null; // null означает, что контейнер убили по таймауту
  durationMs: number;
  timedOut: boolean;
}

function execute(options: ExecuteOptions): Promise<ExecuteResult>;

interface EnsureImageOptions {
  contextDir: string;
  dockerfile: string;
  tag: string;
}

// Собирает образ `tag` из `contextDir`/`dockerfile`, если его ещё нет локально.
// Остаётся домен-агностичной операцией — просто общее удобство, чтобы каждый
// потребитель не переизобретал "собрать свой образ, если он отсутствует".
function ensureImage(options: EnsureImageOptions): Promise<void>;
```

`network` и `onOutput` не входят в более строгую, минимальную версию этого
интерфейса — их добавили, потому что они реально понадобились: шагам `install`
обычно нужен доступ к реестру, а UI сборки хочет стримить вывод по мере
поступления, а не ждать завершения всей команды. Оба поля опциональны и не
протаскивают в пакет никакого доменного понятия.

## Модель безопасности

- Без `--privileged`, без capabilities (`CapDrop: ['ALL']`), `no-new-privileges`.
- Жёсткие лимиты CPU, памяти и числа процессов на каждый запуск.
- Сеть наружу выключена, пока вызывающая сторона явно её не запросит.
- Обязательный таймаут, принудительно убивающий контейнер — зависшая команда не
  подвешивает вызывающую сторону.
- Контейнер всегда удаляется после выполнения, независимо от результата.

Эта модель безопасности одинакова вне зависимости от того, что именно выполняется
внутри — установка пакета из более или менее доверенного репозитория или
произвольная, полностью недоверенная посылка — предположения о недоверенном вводе
применяются к обоим случаям одинаково.

## Требования

Процессу, вызывающему `execute`/`ensureImage`, нужен доступ к Docker-сокету
(`dockerode` по умолчанию подключается к `/var/run/docker.sock`, если не настроено
иначе). Если сам этот процесс работает внутри контейнера с примонтированным
Docker-сокетом хоста (Docker-outside-of-Docker), `workdir` обязан быть путём,
корректно резолвящимся для демона на **хосте**, а не для вызывающего контейнера —
обычно вызывающему процессу нужно самому смонтировать директорию с хоста по
известному пути и транслировать пути соответствующим образом перед вызовом
`execute`.
